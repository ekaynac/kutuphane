## Findings

### 1. Medium: the curator page hides parts of the note the person approves
- **Where:** `src/kutuphane/curatorweb.py:33-45` (`_PENDING`), `curatorweb.py:192-204` (`pending`), `src/kutuphane/curator_ui/core.js:95-104` (`card`).
- **Problem:** the signature covers the note id, a hash of everything in the note: text, scope, citations, links, and a decision's options and choice. The pending view only selects and shows text, kind, scope, class key and writers. It never returns the decision options or choice, the citations, or the `derived_from`/`supersedes` links. §6.6 item 2 and D72 require these on the page.
- **Scenario [INFERENCE]:** an agent writes a `decision_proposal` with harmless text and a harmful `choice`, or a rule with a `supersedes` link. The curator sees only the text, approves, and agents then get that approved choice or rule through `query_notes` and the decision export. Slice Q will rewrite the queue, but slice P's approvals work today.
- **Fix:** return and show every part of the note that its id covers: options and choice, citations, and creation links with the target's text. Do not offer Approve until all of them are shown.

### 2. Medium: approving a rule retires other notes that are not in the signed statement
- **Where:** `src/kutuphane/curation.py:94-106` and `124-125`, `src/kutuphane/passkey.py:337-345` (`_standing_effects`, `EFFECTS`), `core.js:135`.
- **Problem:** `_supersede` writes `retired` events for approved predecessors with `act = NULL`. These predecessors are not in the signed `items`, not shown before signing, and not shown afterwards (the receipt prints only `i.standing`, not `retired`). `verify_acts` only checks rows where `e.act = act`, so it never looks at these retirements.
- **Scenario [INFERENCE]:** an agent writes a rule note B with the same scope as an approved security rule A and a `supersedes` link to A. The curator signs "approve B", and A is silently retired.
- **Fix:**
  - At options time, compute the retirements and put them in the statement (for example `retires: [{ref, id, was}]`), and show them.
  - At act time, write exactly those retirements and refuse with 409 if the set has changed.
  - Make `_standing_effects` also compare the system events whose cause is the act's events.

### 3. Medium: the database policy lets the web role write any "system" Standing value without a signature
- **Where:** `deploy/db-roles-curator.sql:17-23` (the same text is in docs/25 §4.5).
- **Problem:** the `set_by='system'` branch only requires a creation `supersedes` link from a note that some act approved. It does not require `value = 'retired'`, that the target is currently `approved`, the same scope or book, or the same transaction or correlation. Migration 016 has no trigger that enforces Standing transitions.
- **Scenario [INFERENCE]:**
  1. An agent writes rule B that supersedes its own pending note A.
  2. A curator approves B with a passkey.
  3. A compromised curator web inserts `(note_seq=A, value='approved', set_by='system', cause_seq=<B's approval event>)`. The policy accepts it.
  4. `verify-acts` never reports it.
- **Why it matters:** docs/25 §6.5 says the policy allows "exactly these", and §5.6 says `verify-acts` finds rows the web wrote without a signature. Both claims are false for this branch.
- **Fix:** limit the branch to `value = 'retired'`, a target in the same book with the same scope and currently `approved`, and a cause event in the current transaction or correlation. Better: allow it only for retirements listed in the act's statement (finding 2), and check them in a trigger.

### 4. Medium: revoking a passkey does not end its sessions
- **Where:** `src/kutuphane/cli.py:428-436`, `src/kutuphane/passkey.py:277-283` (`session()`).
- **Problem:** the documented response to a lost phone (§3.4) is to revoke the passkey. Revocation only sets `passkey.revoked_at`. `session()` does not check for a live passkey, and there is no command to end sessions or cancel an enrollment.
- **Scenario [INFERENCE]:** someone with the stolen phone, or with the `__Host-kc` cookie, can keep reading `/api/pending` for up to 8 hours after revocation. That includes the full text of private (`restricted`) journal notes. Acts are refused correctly.
- **Fix:**
  - Store the login `credential_id` on `curator_session`.
  - On revoke, set `ended_at` on that passkey's sessions (or all of the person's sessions).
  - Make `session()` require that a `passkey` session's credential is not revoked.
  - Add `curator end-sessions` and `curator cancel-enrollment` commands.

### 5. Low: an enrollment session is not tied to the enrollment code that created it
- **Where:** `src/kutuphane/passkey.py:176-200` (`enrollment_session`, `_enrollment_of`, `registration_options`).
- **Problem:** the session row does not record its enrollment. Registration uses the person's newest live unused enrollment.
- **Scenario [INFERENCE]:**
  1. Code A leaks.
  2. The operator issues code B, which cannot cancel A (no command for it).
  3. An attacker with A registers, and the passkey is recorded against B.
  4. The real person's code B is then refused as "used".
  5. A is still live, so the attacker can register a second passkey.

  The `curator passkeys` list no longer shows which code was actually used, which defeats the operator comparison in §3.4.
- **Fix:** add `curator_session.enrollment` (a foreign key to `curator_enrollment`, required for `login='enrollment'`), use it in `registration_options` and `register`, and add enrollment cancellation.

### 6. Low: the deployment probe passes its Docker checks when Docker can't see the containers
- **Where:** `deploy/curator_probe.py:43-44` and `65-77`.
- **Problem:** `docker()` returns stdout and ignores failure.
  - The Funnel check reads empty output as `{}`, which is PASS.
  - `docker port` on a missing container gives empty output, which is PASS.
  - The "Core cannot reach curator" check passes on any non-zero exit, including "no such container".
- **Scenario:** the docstring says to run the probe from a tailnet device, which usually has none of these containers (or uses another `--compose-project`). The Funnel, published-port and Core-isolation checks all report PASS without testing anything.
- **Fix:** check `returncode` and stderr. Make sure the containers exist (`docker inspect`) before the checks. Inside Core, treat only a connection or DNS error as "unreachable". Fail when `funnel status` gives nothing.

## Checked and rejected (no finding)

- **WebAuthn:**
  - Exact origin; RP ID equal to the origin's host.
  - User verification required at registration, login and act.
  - Raw `crossOrigin`/`topOrigin` refused.
  - `userHandle` required at login and must match the person.
  - Sign counter checked under the memory lock with `FOR UPDATE` and a guarded `UPDATE`. Authenticators that always report 0 pass, as documented.
  - The challenge is SHA-256 of the domain plus the canonical statement, recomputed from the stored row and bound to session, principal and action.
  - One act per challenge and one session per login challenge (unique keys); 5-minute expiry checked with `clock_timestamp()` after the lock.
  - Enrollment codes are 128-bit, hashed and single-passkey, and the trigger rejects expired enrollments.
- **Sessions and browser:**
  - The `__Host-kc` cookie is Secure, HttpOnly and SameSite=Strict, and is new at every login.
  - Every POST checks the exact `Origin` header and a JSON content type.
  - CSP `default-src 'none'` with `frame-ancestors 'none'`, plus `X-Frame-Options: DENY`.
  - The UI uses only `textContent`.
- **Acts:**
  - `was`, note integrity, rights, the D68 rule and the `contradicts` rule are all checked again under the lock.
  - The trigger binds ref, value and reason; the keys bind signer, action and one event per note.
