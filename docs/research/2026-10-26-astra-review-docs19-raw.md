I support the simpler form, with these changes before adoption.

1. **High — Separate format requirements, decision requirements, and human input.** A missing field can still produce a correct `deny` or `escalate`; it cannot necessarily leave the item “usable.” Keep L0’s required identity fields machine-filled. Require additional evidence for the requested operation: rights for permitted use, acceptance for ordinary L2 use, mandate and applicability for requirement authority, activation permission for execution. Origin can remain `unknown`; do not force a guess.

2. **High — Make folder defaults explicit assertions about covered items.** A collection license does not establish its contents’ licenses. Resolve docs/11’s package-license rule against its manifest-default example: a default is valid only when the issuer asserts that it covers those files. Show inherited values and their source in a compact summary; hiding them prevents people noticing exceptions. Preserve `unknown` versus `model`, and absent `ai_use` versus `n`. Also flag that `kstd.init()` currently writes `search: y`, so generated manifests do not start entirely fail-closed.

3. **High — Replace kind-based conditions with behavioral conditions.** Acceptance applies to **every item**, not only policies and procedures. Mandate becomes relevant whenever someone proposes requirement authority. Applicability, exclusions and validity must be accessible for every kind; unknown scope must not silently become universal scope. Keep legal basis at the forwarding operation, but evaluate effective personal-data status, including lineage and untrusted `synthetic` claims. Handling must already constrain proposer/model calls.

4. **High — Repair the provenance dependencies.** Show `inputs` for any derivative, including human and assisted work. Add observation time for recordings and structured generator **name + version** for `tool`. Do not infer “recording” from an empty input list: docs/17 conflicts here with docs/11’s explicit warning that missing lineage proves nothing. Keep reviewer identity conditional on `assisted`, backed by substantive-review evidence. Make `needs_split` available to humans regardless of proposer output.

5. **High — Separate annotation from authorization.** A label confirmation must not itself accept an item, grant a mandate, or authorize activation. Show source acceptance separately from local acceptance and its authorized issuer. `agentfiles.py` supplies positive signals from frontmatter, names, directories and skill membership; a negative match does not prove “not an instruction.” Removing an instruction restriction needs authorized review. Keep trust configuration outside the item form, but show the relevant trust result.

6. **Medium — Keep document kind as a versioned UI preset.** Opening fields is useful presentation behavior under D53, but does not require a core facet. Delete the suggestion that only `procedure + mandate` can impose requirements: docs/11 assigns that behavior to acceptance, mandate and applicability. Presets should reveal fields without hiding existing values or removing restrictions. Allow mixed documents and an “all fields” view.

7. **Medium — Distinguish the dates.** Manifest/statement issuance, source publication, git commit, observation and validity are different facts. Git can propose a source date; it cannot establish observation or validity. Generate statement issuance when the statement is created. Automatic values should be inspectable and correctable where appropriate, rather than “never shown.”

8. **High — Make §5.2 unambiguous: discovery-only tags in version one.** It currently excludes policy tags and then admits them through `policy: true`. Defer that flag. Search/filter membership already satisfies D53; ranking boosts are unnecessary initially. Later policy attributes need defined rules for addition, removal, missing values, conflicts and registry changes. Removing a restrictive tag is a loosening; changing customer membership may both tighten and loosen access. A boolean registry flag is insufficient.

9. **High — Define one tag model with two representations.** Use manifest tags for portable declarations and append-only annotations for later changes. Bind annotations to an exact item version/digest; include issuer, time, action, prior statement and confirmation state. Specify propose → confirm → retract/supersede transitions, concurrent assertions and cross-version carryover. Signatures establish provenance, not authority. Follow the [W3C Web Annotation model](https://www.w3.org/TR/annotation-model/) for tagging bodies and targets, using kstd’s existing DSSE envelope where signatures are required. Current `kstd.py` rejects plain `tags`; introduce a versioned profile/extension explicitly.

10. **Medium — Specify inheritance, visibility and registry identity.** Recommend inherited folder tags plus explicit item additions and exclusions, with provenance visible; preserve the proposal’s no-automatic-inheritance rule for derivatives. Separate private reader tags from shared library tags—`read` should not automatically confer shared-metadata editing rights. Protect tag suggestions, counts and search results with item access rules. Give controlled concepts stable identifiers, namespace ownership, aliases, language labels and deprecation rules; use [SKOS concepts and concept schemes](https://www.w3.org/TR/skos-reference/). Namespace spelling alone is not identity across libraries.

11. **Medium — Make mappings precise and acknowledge information loss.** Map free text to DCAT `dcat:keyword`, controlled subject concepts to `dcat:theme`; not every controlled attribute is a subject theme. [DCAT 3](https://www.w3.org/TR/vocab-dcat-3/) supports that distinction. Map schema.org tags to [`keywords`](https://schema.org/keywords), using `DefinedTerm` where appropriate. Treat [OKF frontmatter `tags`](https://okf.md/spec/) as a string-list interchange convention, pinned to a specification version. These exports do not automatically preserve signatures, policy semantics, inheritance or approval state.

12. **High — Split assisted production from blind evaluation.** Restore docs/09’s approximately 30% blind slice, with proposals withheld server-side and independent adjudication. Split by source/duplicate family to avoid leakage. Freeze proposer versions and compare identical eligible items; docs/16’s denominators differ. Report accuracy, abstention and dangerous errors separately from assisted acceptance rate. Today `collect()` calls unchanged prefills “accepted,” while the server records `claim_source: person`; neither proves independent human judgment. Record exposure, proposal source/version, explicit confirmation, edits and bulk provenance per field.

13. **High — Accelerate evidence review, not blanket agreement.** Keep keyboard navigation, compact inherited summaries and exception controls. Replace unrestricted “accept all” and “same as previous” with field-specific bulk actions, affected-item previews, preserved exceptions and undo. Do not bulk-copy reviewer identity, lineage or authorization merely because files share a folder. Prioritize contradictions and missing provenance. Docs/16’s four missed hostile files and weak acceptance/personal-data results do not support confidence-only approval. Measure total time including deferred review and correction.

14. **Medium — Ask the operator about the missing product decisions.** Which operation must an item become ready for first? Who may assert folder-wide rights and approve loosening? Are tags private, team-shared or exported? Do tags target books, files or blocks, and should they follow changed versions? Is unknown provenance acceptable, with later review? What dangerous-error rate and blind-evaluation budget are acceptable?
