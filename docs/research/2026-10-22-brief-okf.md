## 2. What we bring

- `src/kutuphane/kstd.py`: the L0 validator. It checks SPDX expressions (against `spdx_ids.txt`), one `sha256` digest for each file, `ai_use` y/n and `personal_data`. Its YAML loader refuses aliases and duplicate keys.
- `kstd/README.md`: what Kütüphane does with these fields:
  - `search` is not `y`: the file is not indexed;
  - `ai_input` is not `y`: the text never goes to a model;
  - `personal_data` is not `no`: export needs a legal basis.
- `docs/11-standard-draft.md`: §4 rules 4 and 8, §5 Rights, §8 example.
- `kstd/tests/decision/cases.yaml`: the rule-4 cases (lines 135–181) and `kstd/reference/decide.py`.
- `src/kutuphane/source.py`: it reads OKF bundles, keeps the bytes unchanged (so unknown keys survive) and records `type`.
- `src/kutuphane/packages.py` and the `cli.py` `approve-import` command: an import is published with **this** installation's policy. The sender's policy is only a suggestion.
- **Gap:** D60 is not yet in the code. `ORIGINS` and `PERSONAL_DATA` still have three values each. `effective()` fills an absent `ai_use` term with `n`. There is no `legal_basis` field in L0; it is only the `--legal-basis` export flag.

## 4. Reason

- **For them:** kc#52 asks for a license key, and that request is now at a frozen location. We give the license key, plus the AI-use and personal-data terms that their agent-consumption goal needs. We also give a validator and test cases. In the #15 thread nobody has said that restrictions must travel when trust does not.
- **For us:** OKF is our L0 shape (D21). If OKF uses our names, a plain OKF bundle carries kstd rights without `kstd.yaml`, and other tools keep the values.

## 5. Consequences

- **IPR:**
  - The W3C CLA **does not apply**. OKF needs the Google CLA ([CCLA text](https://cla.developers.google.com/about/google-corporate)).
  - The company keeps the copyright. It gives Google and recipients a perpetual, irrevocable copyright license.
  - It also gives a patent license for claims *"necessarily infringed"* by the contribution together with the Work. Whether the company has relevant patents is not verified.
  - The CCLA's definition of "submitted" includes *"issue tracking systems."* Thus issue and comment text are Contributions too.
  - Our text is already CC-BY-4.0, so there is no conflict.
- **If they accept:**
  - Kütüphane reads `rights` from frontmatter (`source.py`).
  - When frontmatter and `kstd.yaml` do not agree, the stricter value wins.
  - `kstd.yaml` becomes a profile: folder defaults and digests.
  - If they choose flat `license` (kc#52), we map it to `rights.license`.
- **If they reject, or do not reply:**
  - We keep `kstd.yaml`.
  - We write `rights:` as an extension key, with the same names.
  - Risk: a future OKF key with the same name and a different meaning.
- **Effort (estimate):**
  - CCLA: 1–3 days of company time.
  - Adapting the two drafts: about 3 h.
  - Follow-up: about 1 h each week for 6 weeks.
  - A later PR to SPEC.md with an example bundle and tests: about 1–2 days.
- **Risks:**
  - The maintainers do not answer, and more than 20 proposals compete.
  - "Absent = no" would block every existing bundle for agents. That is why the draft leaves the default to the consumer.
  - The AIPREF vocabulary can still change.
  - Readers can take `personal_data` as a compliance claim. Say "declared, not verified".
  - Google controls the format, with no neutral governance.

## 7. Draft text

### A. New issue

**Title:** Proposal: optional `rights` family (SPDX license, AI-use terms, personal data) and `sources[].digest`

> Continues GoogleCloudPlatform/knowledge-catalog#52, which was filed against the frozen `okf/` copy. Related: #15, #32.
>
> **Problem.** A bundle travels (§1, goal 3). From the frontmatter, a reader cannot tell three things: if it may reuse a concept, if it may give the concept to a model, and if the concept contains personal data. Unknown-key tolerance (§4.1) lets each producer invent its own spelling. Also, `sources` cannot pin the exact bytes a concept came from.
>
> **Proposal.** One optional family, in the same style as `generated`:
> ```yaml
> rights:
>   license: CC-BY-4.0            # SPDX license expression, or `unknown`
>   holder: "Example Org"         # cf. dcterms:rightsHolder
>   ai_use: { search: y, ai_input: y }   # train: not stated
>   personal_data: "yes"          # yes | no | unknown | synthetic
>   legal_basis: eu-gdpr:A6-1-b   # a DPV concept; only with personal_data: yes
> sources:
>   - id: policy-v3
>     resource: https://example.com/policy-v3.pdf
>     digest: sha256:<64 lowercase hex>
> ```
> 1. Every key is optional. Absent means **not stated**. A producer MUST NOT write `n`, `no` or `unknown` for a term that was not stated. Each consumer chooses its own default. A consumer SHOULD NOT read "not stated" as a permission.
> 2. A `license` value that is not valid SPDX counts as `unknown`. `unknown` grants nothing.
> 3. The `ai_use` terms `search`, `ai_input` and `train` map to Cloudflare Content Signals and IETF AIPREF. YAML 1.1 loaders read `y`, `n`, `yes` and `no` as booleans. Consumers MUST read `true`/`false` as `y`/`n` (as `yes`/`no` for `personal_data`).
> 4. `synthetic` means: this looks like personal data but describes no real person. A consumer SHOULD treat it as `unknown` unless it trusts the producer.
> 5. A concept cannot carry the digest of its own file. Whole-file digests belong to packaging.
> 6. Consumers MUST NOT reject a concept because a `rights` value is missing or invalid (§11). They SHOULD treat an invalid term as not stated.
> 7. A tool that re-emits a concept keeps `rights` unchanged or makes it stricter (see #15).
>
> **Flat or nested (#52).** v0.2 already uses families (`generated`, `verified`). A consumer MAY read a top-level `license` as `rights.license`.
>
> **Test cases**
>
> | Input | Expected |
> |---|---|
> | no `rights` | all terms not stated; the concept is conformant |
> | `license: "Apache 2"` | `unknown`; the concept is not rejected |
> | `ai_use: {search: y}`, re-emitted | the output has no added `ai_input: n` |
> | `personal_data: yes` (unquoted) | read as `yes` |
> | `digest` does not match the fetched source | the consumer shows that the source changed; it does not reject |
>
> A reference validator and cases (Apache-2.0): `<public link>`. This change is additive (§12, minor version).

### B. Comment on #15

> +1 to "reportable, not inherited". Kütüphane, an on-prem library that reads OKF bundles, applies the same rule. It publishes an import only with the receiver's policy. A change that tightens applies from any source. A change that loosens applies only if the receiver trusts that source for that kind, scope and action, with an expiry.
>
> Two additions:
> 1. **Restrictions go the other way: they are inherited.** If A says `ai_input: n` or gives a license, B must carry that value unchanged or stricter. If not, the import launders rights the same way option 1 launders trust.
> 2. **Pin what was observed.** Add an optional `imported[].digest`: the sha256 of the upstream file at `at`. Then C can check that "human-reviewed in A" applies to these exact bytes.
>
> Test case. A's concept has `verified: {by: human:alice}` and `rights.ai_use.ai_input: n`. B imports it with `imported` and adds no local `verified`.
> Expected: B's tier is *unverified*. B shows "human-reviewed in A". If B writes `ai_input: y`, B is non-conformant. If C can read A, C uses `n`.
