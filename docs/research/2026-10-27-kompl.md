# Kompl (github.com/tuirk/Kompl): what it is, how it compares with Kütüphane/kstd, and whether it makes our work redundant

I read the repo at commit `81badaa` (README, AGENTS.md, CHANGELOG, the SQLite schema v30, the agent-source code, the MCP server and the issues). I used `gh api` for all counts.

## 1. What it is and who it is for

- **It is a "compounding LLM-wiki" for one person, used as a second brain.** You save links, PDFs, threads, bookmarks, Apple Notes or YouTube videos. A cloud LLM (DeepSeek or Gemini; Firecrawl is also required) then writes and rewrites linked wiki pages with citations. Your agent reads these pages over MCP. ([README](https://github.com/tuirk/Kompl#readme))
- **It follows Karpathy's "LLM Wiki" pattern.** That [gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) is dated 2026-04-04, and Kompl was created on 2026-04-08. The README does not cite the gist.
- **Stack:**
  - a Next.js app with a SQLite database;
  - a FastAPI NLP service (spaCy, TF-IDF, KeyBERT, MiniLM embeddings, Chroma);
  - n8n, which has a non-OSI licence, as a runtime dependency.
- **Licence:** Apache-2.0.
- **Activity (2026-10-27):**
  - 81 stars, 7 forks, 2 watchers.
  - 9 releases, from v0.1.0 (2026-04-27) to v0.4.0 (2026-10-26).
  - 462 commits on main: 413 by `tuirk`, 48 by dependabot, 1 by `ahjinsolo`.
  - 14 issues, 5 open. Only 3 issues come from outside people (#104, #139, #140).
  - So it is in effect a one-person project, but a careful one: about 250 test files, an integration test of each MCP tool, OpenSSF Scorecard and validation reports.
- **Maintainer:** Tuana Irkey, "Knowledge management practitioner". Her profile gives her location as Turkey and her company as PivotGround OÜ.
- **Limits that the project states itself:** "Single-tenant only: no user accounts or access control." Markdown output is not sanitized, so there is a known XSS gap.

## 2. How it stores and describes knowledge

- **Sources** table:
  - `title`, `source_type`, `source_url`, `content_hash`, `file_path`, `status`, `date_ingested`;
  - `metadata` (JSON), `published_at` and `published_at_source`.
- **Pages** are markdown files whose frontmatter holds only four fields: `title`, `page_type`, `category`, `summary`.
  - Page types: entity, concept, comparison, overview, source-summary, original-source.
  - The database also stores `previous_content_path` and `draft_rules`.
- **Provenance** table: `source_id`, `page_id`, `content_hash`, `date_compiled`, `contribution_type`. Pages cite sources as `[^source_id]` footnotes.
- **Relations** (`relationship_mentions`) store the source sentence (`quote`) and a `quote_verified` flag.
- **Disagreements and claim verdicts** record `found_by`, `kind`, `status`, `owner_verdict`, the judging `model`, and which claim is `newer`.
- **Export formats:** Markdown, Obsidian, JSON and a `.kompl.zip` backup. None of these is a published or specified format.

## 3. Coverage of governance features

| Topic | Kompl |
|---|---|
| Provenance | At source → page level. In [#104](https://github.com/tuirk/Kompl/issues/104) the maintainer says: "Coarser level only: source → page." v0.4 adds verified quotes for relations. |
| Human vs AI origin | No field. See §4. |
| Rights / licences | **None.** The code has no licence, SPDX or ai_use field. |
| Personal data | **None.** All source text goes to DeepSeek or Gemini. There is no local-model option. |
| Approval | A draft queue with approve and reject. `auto_approve` is **on by default** (`db.ts`: `getSetting('auto_approve') !== '0'`). There is only one user. |
| Versions | The last two versions of each page, with a restore action. |
| Supersession | The claim check marks a claim as "changed" when a newer source changes it, and uses source dates for this. Sources are immutable snapshots. |
| Trust | No issuers, no signatures and no authentication. Kompl answers only to localhost and its own host names. |
| Agent access | An MCP server with 8 tools: `search_wiki`, `research_topic`, `read_page`, `read_source`, `list_sources`, `recent_changes`, `wiki_status`, `add_source`. `add_source` is off by default and is limited to 5 items per call and 20 per day. `fence.ts` puts all wiki text in a `<wiki-data-RANDOM>` tag, as protection against prompt injection. |
| Policy decisions | Only switches and a daily spend cap. There is no decision rule. |

## 4. How it separates human text from AI text

- **Wiki pages:** the LLM writes all of them. The only exception is the `original-source` page type, which holds a copy of the user's own text. There is no page-edit API: I found only `restore-previous` (a POST). So humans curate sources and give verdicts, and the model writes every page.
- **Sources from an agent:** a source added through `add_source` gets `metadata: {added_via: 'mcp', client}` (`agent-sources.ts`), and the activity log records `agent_sources_added`.
  - `client` is the name that the MCP client reports for itself (`getClientVersion()?.name`). Nothing checks it.
  - A source added through the UI has **no marker**.
- **The open gap:** `/api/onboarding/stage` and `/api/onboarding/finalize` have no authentication. The cross-site check blocks only browser requests that send an `Origin` header; requests without one pass. So an agent with a shell can call these routes with `curl`, and its source then looks exactly like a human's. This is the same human-vs-agent problem that the operator asked about. Kompl does not try to solve it.

## 5. Feature comparison

| Their feature | Ours | Who is ahead | Note |
|---|---|---|---|
| Automatic synthesis: the LLM writes and updates linked pages, resolves entities, draws a topic map | Answers with passage citations; no compiled wiki | **Kompl** | This is their main value. We do not do it. |
| Connectors: URL, YouTube, bookmarks, Twitter, Apple Notes, Office files | Folders (markdown, PDF, text formats, HTML) | **Kompl** | Our scope is governed folders, not personal capture. |
| Contradiction detection by a claim check, with an owner verdict | `contest` statement, signed by a person; no automatic detection | Kompl on detection, ours on accountability | Their detector could create proposals for our `contest` statements. |
| Citations: footnotes per page, verified quotes for relations | Passages with line numbers | About equal | Ours are finer for answers; their verified quotes are a good idea. |
| Format: SQLite, 4 frontmatter fields, zip backup | `kstd.yaml` (L0) and an open draft standard | **Ours** | They have no portable or specified format. |
| Rights / licence | SPDX licence and `ai_use` search/ai_input/train | **Ours** | They have nothing. |
| Personal data | `personal_data` plus a DPV legal basis for export | **Ours** | They send everything to the cloud. |
| Origin | Implicit (page type, `added_via: mcp`) | **Ours** | We have 5 values plus `reviewed_by` and `software_agent`. |
| Approval | Draft queue, auto-approve on, one user | **Ours** | We have acceptance with approver ≠ author, and delegation. |
| Versions | Last 2 versions of a page | **Ours** | We have digests, versioned books and signed packages. |
| Supersession | Claims marked "changed" by date | Both, in different ways | Ours is formal (withdrawal with a successor, status streams). Theirs finds changes in content. |
| Trust / authentication | None (single-tenant) | **Ours** | We have OIDC principals and issuer trust. |
| MCP | 8 tools, injection fence, gated writes | About equal | Their fence and their `research_topic` design are worth a study. |
| Policy | Spend cap and switches | **Ours** | We have a deterministic permit/deny/escalate rule with conformance cases. |
| Model locality | Cloud only | **Ours** | We run on-prem and air-gapped through LLMDAP. |
| Adoption and polish | 81 stars, one-line installer, demo video | **Kompl** | Our repo `ekaynac/kutuphane` has 0 stars and 0 forks (created 2026-10-07). |

## 6. What we can learn, reuse, or do together

- **Reuse:**
  - **The injection fence** (`mcp-server/src/fence.ts`): a random tag for each result, plus look-alike and invisible-character handling. It is Apache-2.0, so we can adapt it with attribution.
  - **`quote_verified`:** each extracted relation keeps its source sentence, and the code checks that sentence against the source. This is cheap evidence for derived items.
  - **Separate source dates:** `published_at` plus `published_at_source`. This matches our "dates are different facts" rule in docs/19 §3.2.
  - **Write gates for agents:** off by default, a limit per call and per day, and a log entry for each write.
- **Learn from their communication:** one clear user benefit, a 1-minute demo and a one-line installer. Our value is invisible until a user meets a deny or an escalate.
- **Cooperation:** there is a real opening. In #104 the maintainer says that authority work ("establishing what an item is, where it came from…") happens before Kompl, in an unpublished "pre-kompl". That is exactly the kstd layer. Concrete steps:
  1. A Kompl source connector that reads `kstd.yaml`: it skips files whose `ai_use.ai_input` is not `y`, carries the licence and origin into `sources.metadata`, and blocks the cloud LLM for personal data.
  2. Export Kompl pages as kstd items with `origin: model`, their `inputs` (the provenance table) and the judging model. This would be a real test of our derived-item rules.
  3. Open an issue to propose the connector and point to their own #104 text. The maintainer also lists her location as Turkey, so contact may be easy. Whether she wants this is not verified.

## 7. Does it make our work redundant?

**No. But it shows where our work is weak.**

- **Kompl answers a different question.** It asks: "How do I turn my saved material into a useful wiki with no work?" We ask: "May this item be used, by whom, for what, and who accepted it?" Kompl has no rights, no personal-data rules, no acceptance by a second person, no trust and no local models. It could not legally run on regulated organisational knowledge in its present form.
- **The honest criticism:**
  - Kompl delivers visible value on the first day. We deliver mostly refusals and metadata.
  - Its 81 stars after 6 months, for a polished one-person tool, show that individual users do not ask for governance. Our users must be organisations that must comply. That market is smaller and slower, and we must find it on purpose.
  - Kompl shows that the *synthesis* layer is what users see. If we never derive anything, our derived-item rules in kstd stay untested.
- **The risk is not redundancy. The risk is that a tool like Kompl adds a "provenance" checkbox before kstd has any users.** A Kompl connector for kstd would be a small step to cut that risk.
