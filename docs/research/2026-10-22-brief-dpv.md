# Brief: W3C DPV Community Group (DPVCG)

The two concepts that `docs/13` says DPV lacks are **already in DPV**:
- `dpv:SyntheticData` has existed since 2022.
- "Personal data presence unknown" can be written with the DPV Applicability pattern from [#102](https://github.com/w3c-cg/dpv/issues/102): `dpv:hasPersonalData dpv:UnknownApplicability`.

Thus do not file a "presence unknown" concept. It would duplicate an existing concept. Correct `docs/13` §4 row 4 and §6 Q4.

**A. Comment on #221**

> Use case: a folder manifest that uses DPV as a code list, without RDF. kstd (Apache-2.0 code, CC-BY-4.0 text, <link>) is a YAML file next to the files. It matches @tobie's case. Invented example:
> ```yaml
> rights: {license: CC-BY-4.0, ai_use: {train: n}, personal_data: no}
> items:
>   - {path: hr/checklist.md, digest: "sha256:…", rights: {personal_data: yes}}
>   - {path: test/fake-customers.csv, digest: "sha256:…", rights: {personal_data: synthetic}}
>   - {path: inbox/scan-0042.md, digest: "sha256:…", rights: {personal_data: unknown}}
> ```
> At export, our tool requires a basis for `yes` and `unknown`, and records it: `legal_basis: [eu-gdpr:A6-1-b]`, `vocab: https://w3id.org/dpv/2.3/legal/eu/gdpr`.
>
> | kstd | DPV |
> |---|---|
> | yes | `dpv:hasPersonalData dpv:PersonalData` (or a `pd:` category) |
> | no | `dpv:hasPersonalData dpv:NotApplicable` |
> | synthetic | `dpv:hasData dpv:SyntheticData` |
> | unknown | `dpv:hasPersonalData dpv:UnknownApplicability` |
>
> For us, a flat file needs `id` (CURIE), `iri`, `label`, `definition` and `parents`, with the `versionIRI` in the file (#492) and a stated membership rule (#484). The legal-basis slice and the data/applicability slice are enough for us.
> Questions: (1) Is `hasPersonalData UnknownApplicability` the intended way to say "not assessed" (#102)? (2) Is `NotApplicable` correct for "no personal data", or do you prefer `NonPersonalData`? We can test a draft file with our validator.

**B. Concept request**: `[NEW]: v2.5 – usage note and relation for dpv:SyntheticData`

> Specs: DPV
> Term: SyntheticData (existing)
> Parent term: GeneratedData. Proposal: add NonPersonalData as a broader concept, or state that the term does not imply NonPersonalData.
> Source: GDPR Recital 26 (anonymous information).
> Usage note: "SyntheticData alone does not state that no personal data is present. Synthetic data that a model generates from personal data can contain records of real persons. To state absence, also use `hasPersonalData NotApplicable`. Where this is unknown, use `UnknownApplicability`."
> Justification: rule engines and flat lists (#221, #484) must decide whether a legal basis is necessary. `GeneratedData` says "not derived", but synthetic data from a model often comes from training data.
> Test: `{hasData: SyntheticData}` → status unknown (basis required). `{hasData: SyntheticData, hasPersonalData: NotApplicable}` → no basis required.
